# SNN News Resume Redesign

## 1. 목적

완성된 Vanilla 포트폴리오를 김성원의 경험과 생각을 전하는 개인 뉴스 사이트로 다시 디자인한다. 결과물은 취업용 포트폴리오의 전형적인 카드 모음보다 한 사람을 취재한 특집 기사처럼 읽혀야 한다.

CNN의 검정 헤더, 붉은 강조색, 강한 헤드라인, 비대칭 기사 그리드 같은 정보 위계는 참고하지만 로고와 콘텐츠는 그대로 모방하지 않는다. 사이트 브랜드는 **SNN — Sungwon News Network**로 정하고, 모든 기사 제목과 본문은 사용자의 말투를 살린 존댓말 인터뷰 형식으로 작성한다.

이번 변경은 시각적 개인화와 콘텐츠 교체가 핵심이다. 기존 과제의 HTML, CSS, JavaScript 학습 목표와 필수 기능은 모두 유지한다.

## 2. 성공 기준

1. 첫 화면에서 개인 뉴스 사이트라는 인상과 김성원의 핵심 개발 서사가 동시에 드러난다.
2. About, Skills, Projects, Contact를 포함한 과제 필수 섹션을 뉴스 문법 안에서 자연스럽게 찾을 수 있다.
3. 개발 계기, 코디세이 미션 회고, 학습 방식, 관심 기술, 취미와 《광마회귀》 감상이 인터뷰 기사로 읽힌다.
4. GitHub 프로젝트는 API로 받은 실제 저장소 정보와 해당 README의 로컬 캡처를 함께 보여준다.
5. 모바일·태블릿·데스크톱에서 기사 위계가 무너지지 않고 한 열부터 여러 열까지 자연스럽게 재배치된다.
6. 기존 인터랙션, API 상태, 폼 검증, 테마 저장과 GitHub Pages 배포 요구사항이 계속 동작한다.

## 3. 범위

### 필수 범위

## 4. 콘텐츠와 정보 구조

### 뉴스룸 헤더

검정 바탕의 고정 헤더에 메뉴 버튼, SNN 워드마크, 섹션 링크, 테마 전환 버튼을 배치한다. 데스크톱에서는 링크를 한 줄로 보여주고 모바일에서는 햄버거 메뉴로 접는다.

내비게이션 항목은 `About`, `Learning`, `Missions`, `Projects`, `Life`, `Contact`로 구성한다. 항목은 모두 페이지 내부의 시맨틱 섹션으로 이동한다.

헤더 아래의 `Developing Story` 띠에는 현재 관심사를 짧게 나열한다. 자동으로 계속 움직이는 티커는 읽기와 접근성을 방해하므로 기본 구현에서는 정적인 가로 목록으로 만들고 좁은 화면에서만 가로 스크롤을 허용한다.

### 1면 특집

데스크톱 첫 화면은 세 열의 비대칭 기사 구성이다.

* 왼쪽: 프로필 이미지와 개발을 선택한 배경
* 중앙: 가장 큰 헤드라인과 인터뷰형 소개
* 오른쪽: 코디세이 참여 계기와 앞으로의 관심사

중앙 헤드라인은 사용자의 핵심 서사를 한 문장으로 압축한다. 예: “여러 환경을 경험하고 싶어 개발을 선택했습니다.” 본문은 딱딱한 자기소개서 문장이 아니라 질문과 답변이 이어지는 인터뷰 톤으로 다듬는다.

개인 프로필 사진이 구현 시점에 제공되지 않으면 현재 로컬 자리표시 이미지를 SNN 스타일의 흑백 인물 프레임으로 사용한다. 이후 `images/profile/`의 파일만 교체해 레이아웃 변경 없이 실제 사진으로 바꿀 수 있게 한다.

### Codyssey Missions

미션 1~3을 독립 기사로 배치한다. 각 기사는 과제 설명보다 다음 흐름을 우선한다.

```text
무엇을 만들었는가
→ 어디에서 막혔거나 흥미를 느꼈는가
→ 무엇을 배웠는가
→ 다음 프로젝트에서 무엇을 다르게 할 것인가
```

미션 3은 가장 큰 회고 기사로 다룬다. Superpowers와 SOLID를 적용해 설계를 세분화했지만 AI에 네이밍과 구현을 많이 맡기면서 코드 흐름을 놓친 경험, 평가를 통해 완성과 이해가 다르다는 점을 확인한 경험을 핵심으로 삼는다.

### Learning / Skills Desk

기술 목록을 단순 배지로만 보여주지 않는다. HTML, CSS, JavaScript, Git, Python, Docker처럼 실제로 사용한 기술을 짧은 편집국 메모 형식으로 설명한다. 각 항목은 “어디에 사용했는지”를 한 줄로 덧붙여 기술과 경험을 연결한다.

학습 방식 기사는 하나의 스토리로 연결해 배우는 습관과 자신의 언어로 설명할 수 있어야 한다는 기준을 담는다.

### GitHub Projects

각 프로젝트는 하나의 취재 기사다. 기사 제목은 저장소 이름 또는 읽기 좋은 표시 이름을 사용하고, 본문에는 해당 과제에서 배운 점과 판단 근거를 넣는다.

대상 저장소는 우선 다음 네 개다.

* `codyssey_misson1`
* `codyssey_mission2`
* `codyssey_mission3`
* `web-resume-vanilla`

각 카드 상단에는 실제 README 첫 부분을 캡처한 로컬 이미지를 일정 높이로 잘라 보여준다. 캡처는 장식이 아니라 프로젝트 내용을 미리 보여주는 기사 이미지이므로 저장소와 내용을 설명하는 `alt`를 제공한다.

### Life

러닝, 웹툰·무협지, 최근 완독한 《광마회귀》, 헤드폰을 계기로 시작한 음악 감상을 한 섹션 안의 짧은 문화 기사들로 묶는다. 개발 기사와 시각적으로 구분하되 사이트 전체의 편집 문법은 유지한다.

### Contact / Footer

문의 폼은 `Send a Tip` 기사 제보함처럼 표현한다. 이름, 이메일, 메시지 필드와 기존 검증 기능을 유지하고 실제 전송이 아닌 학습용 확인 상태라는 점을 명확히 표시한다.

검정 푸터에는 SNN 이름, 저작권, GitHub 링크, 맨 위로 이동하는 수단을 배치한다.

## 5. 시각 디자인

### 디자인 언어

* 주조색: 검정, 흰색 또는 따뜻한 회백색
* 강조색: 뉴스 속보를 연상시키는 붉은색
* 제목: 굵고 압축된 산세리프 계열
* 본문: 긴 한국어 기사를 읽기 편한 산세리프 또는 명료한 고딕 계열
* 구분: 붉은 상단선, 검정 구분선, 충분한 여백
* 이미지: 정해진 비율로 크롭하고 기사 캡션을 제공

초기에 논의한 낡은 종이 질감과 정통 브로드시트 장식은 CNN형 방향으로 전환하면서 제외한다. 대신 기사 밀도와 편집 위계로 뉴스의 인상을 만든다.

### 레이아웃

모바일 우선으로 한 열에서 시작한다. `768px` 이상에서는 두 열 기사 배치를, `1024px` 이상에서는 1면의 비대칭 세 열과 프로젝트 다열 그리드를 사용한다.

내비게이션은 Flexbox를 사용하고 프로젝트 목록은 과제 조건에 따라 `auto-fit`과 `minmax()` 기반 CSS Grid를 유지한다. CSS 변수로 색, 글자 크기, 간격, 선, 그림자를 정의한다.

카드 그림자는 뉴스 지면의 평면적인 느낌을 해치지 않을 정도로 제한적으로 사용한다. hover와 transition은 링크나 카드가 상호작용 가능하다는 사실을 전달하는 데만 사용한다.

### 테마

다크 모드는 `Night Edition`, 라이트 모드는 `Day Edition`으로 해석한다. 기존 `data-theme`와 `localStorage` 흐름은 유지하고 색상 변수만 뉴스 디자인에 맞게 교체한다.

## 6. 기술 구조

기존 기능별 스크립트 구조를 유지한다.

```text
index.html
css/style.css
js/navigation.js
js/theme.js
js/scroll.js
js/contact.js
js/projects.js
images/
  profile/
  projects/
```

* `index.html`: 기사 의미와 정적인 인터뷰 콘텐츠를 소유한다.
* `style.css`: 뉴스 디자인 토큰, 기사 레이아웃, 테마, 반응형 규칙을 소유한다.
* `navigation.js`: 햄버거 메뉴와 부드러운 섹션 이동을 소유한다.
* `theme.js`: Day/Night Edition 상태와 저장을 소유한다.
* `scroll.js`: 헤더 변화, 맨 위 버튼, 기사 등장 효과를 소유한다.
* `contact.js`: 제보 폼의 입력·오류·성공 상태를 소유한다.
* `projects.js`: GitHub API 상태, 로컬 편집 정보와 API 응답 결합, 프로젝트 렌더링을 소유한다.

새 프레임워크나 빌드 단계를 추가하지 않는다. 이번 과제의 학습 대상인 DOM, 이벤트, 상태 변경, 렌더링 흐름을 코드에서 직접 읽을 수 있어야 하기 때문이다.

## 7. 프로젝트 데이터 설계

`projects.js`에 저장소 이름을 키로 하는 소규모 로컬 편집 데이터 맵을 둔다.

```text
repository name
→ 표시 제목
→ 인터뷰 요약
→ README 캡처 경로와 대체 텍스트
→ 표시 순서
```

GitHub API 응답은 같은 저장소 이름으로 이 맵과 결합한다.

```text
페이지 로드 또는 다시 시도
→ loading 상태 렌더링
→ GitHub 저장소 요청
→ 응답 검증
→ 관심 저장소만 filter
→ 로컬 편집 정보와 map으로 결합
→ success 또는 empty 상태 렌더링
```

API에서 가져오는 값은 저장소 URL, 설명, 언어, 별 개수, 최종 수정 시각 등 실제 변할 수 있는 정보다. 인터뷰 요약과 README 캡처는 사이트가 소유하는 정적 콘텐츠다.

README를 실시간 Markdown으로 가져오지 않는 이유는 외부 파서 없이 안전하게 렌더링하는 복잡성이 이번 미션의 범위를 벗어나기 때문이다. 로컬 캡처는 구현이 단순하고 시각 결과가 안정적이며 이후 이미지 파일만 쉽게 교체할 수 있다. 대신 README가 바뀌면 캡처도 수동으로 갱신해야 한다.

## 8. 주요 상태와 데이터 흐름

### 메뉴

```text
메뉴 버튼 click
→ 열림 상태 계산
→ active 클래스와 aria-expanded 갱신
→ 모바일 메뉴 표시 변경
```

### 테마

```text
초기 로드
→ localStorage 조회
→ Day/Night 상태 결정
→ data-theme와 버튼 설명 렌더링

테마 버튼 click
→ 상태 반전
→ 화면 렌더링
→ localStorage 저장
```

### 프로젝트

```text
load 또는 retry click
→ loading
→ fetch
→ success | empty | error
→ 상태별 기사 그리드 또는 안내와 재시도 버튼 렌더링
```

403 응답은 GitHub 비인증 요청 한도 안내를 포함하는 error 상태로 처리한다. 원격 문자열은 HTML 삽입 전에 이스케이프하고 외부 링크는 GitHub HTTPS URL만 허용한다.

### 제보 폼

```text
input
→ 해당 값과 오류 상태 갱신
→ 필드 오류 렌더링

submit
→ 기본 전송 방지
→ 전체 값 정규화와 검증
→ 오류 또는 학습용 성공 메시지 렌더링
```

### 스크롤

```text
scroll
→ 위치 계산
→ 헤더 compact 상태와 맨 위 버튼 표시 갱신

IntersectionObserver
→ 기사 진입 감지
→ reveal 클래스 적용
```

`prefers-reduced-motion` 사용자는 부드러운 이동과 등장 효과를 최소화한다.

## 9. 오류와 대체 상태

* GitHub loading: 프로젝트 취재 중이라는 문구 또는 스피너
* GitHub empty: 표시할 프로젝트가 없다는 기사형 안내
* GitHub error: 불러오지 못한 이유와 다시 시도 버튼
* GitHub 403: 요청 한도 가능성을 구체적으로 설명
* 이미지 실패: 의미 있는 대체 텍스트가 내용을 대신함
* 저장소 매핑 누락: 알려진 안전한 기본 표시 정보 사용 또는 해당 항목 제외
* `localStorage` 사용 불가: 현재 페이지에서는 테마가 동작하고 저장만 생략
* `IntersectionObserver` 미지원: 기사를 즉시 표시

## 10. 검증 전략

자동화 도구를 새로 도입하지 않고 현재 프로젝트의 브라우저 검증 방식을 확장한다.

* 최신 Chrome에서 320px, 768px, 1024px 이상 레이아웃 확인
* 키보드만으로 메뉴, 링크, 테마, 프로젝트 재시도, 폼, 맨 위 버튼 조작
* 모든 이미지의 `alt`, 폼 `label`, 제목 계층, landmark 확인
* Day/Night 전환과 새로고침 후 유지 확인
* 프로젝트 loading, success, empty, 일반 error, 403 상태 확인
* 잘못된 이름·이메일·메시지와 정상 폼 입력 확인
* 모션 축소 설정에서 스크롤과 reveal 동작 확인
* 콘솔 오류와 수평 오버플로 확인
* 로컬 확인 후 GitHub Pages에서도 상대 경로, API, 테마, 폼을 다시 확인
* README에 완성 화면과 배포 주소 갱신

## 11. 구현 순서

1. 개인 콘텐츠, 기사 제목, 이미지 자산 목록 확정
2. 시맨틱 HTML을 SNN 기사 구조로 재작성
3. 뉴스 디자인 토큰과 모바일 기본 레이아웃 작성
4. 768px/1024px 기사 그리드와 헤더 반응형 작성
5. 기존 내비게이션·테마·스크롤 기능을 새 DOM에 연결
6. GitHub 사용자와 로컬 프로젝트 편집 데이터를 교체하고 README 캡처를 결합
7. Contact를 Send a Tip UI로 바꾸고 검증 동작 확인
8. 접근성, 반응형, 네 가지 API 상태, 브라우저 콘솔을 통합 검증
9. README와 학습 기록을 갱신하고 GitHub Pages에 재배포

HTML 구조를 먼저 고정해야 CSS와 JavaScript 선택자가 안정되므로 이 순서를 사용한다. 프로젝트 데이터는 정적 기사 구조가 확정된 뒤 결합해 한 번에 한 종류의 문제만 다룬다.

## 12. 학습 마일스톤

### Milestone 9.1 — 기사 구조와 시맨틱 HTML

뉴스 기사에서 `header`, `nav`, `main`, `section`, `article`, `footer`가 어떤 의미를 맡는지 현재 화면과 연결해 학습한다.

### Milestone 9.2 — 편집 위계와 반응형 CSS

모바일 한 열이 태블릿과 데스크톱의 여러 열로 바뀌는 과정, Flexbox와 Grid를 선택한 이유, 시각적 위계와 문서 순서의 차이를 학습한다.

### Milestone 9.3 — 기존 이벤트를 새 UI에 다시 연결

디자인을 바꿔도 메뉴, 테마, 스크롤 기능의 event → state → render 구조가 유지되는 이유와 DOM 선택자 계약을 학습한다.

### Milestone 9.4 — 로컬 콘텐츠와 원격 데이터 결합

고정된 인터뷰·이미지와 GitHub API의 변하는 메타데이터를 저장소 이름으로 결합하면서 `fetch`, `filter`, `map`, 비동기 상태를 복습한다.

### Milestone 9.5 — 검증과 재배포

코드 변경이 Git commit, GitHub Pages, HTTPS 요청, 브라우저 파싱과 렌더링을 거쳐 새 화면으로 보이는 전체 흐름을 다시 확인한다.

질문식 시험은 진행하지 않는다. 각 마일스톤에서 구현에 필요한 내용을 먼저 설명하고, 중요한 설계 근거와 이후 학습할 심화 주제는 기록으로 남긴다.
